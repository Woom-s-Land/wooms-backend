# Netty 이력서·면접 근거 메모

기록일: 2026-11-03
기준: wooms-socket `13dc6b1`, backend `e45b732`, frontend `76750f0`.

## 사용자 의도

Netty의 설계 정책과 선택 이유를 이후 이력서·포트폴리오·면접에 활용한다. 단순 라이브러리 교체보다 문제, 설계 결정, 트레이드오프, 검증 근거를 중심으로 설명한다. 아래 구현 사실과 개선 계획을 혼동하지 않는다. 운영 도입·장기 안정성·성능 향상을 달성했다고 쓰지 않는다.

| 개인 역할·오류·초기 상태를 해당 연결 구독으로 전달 | 방 방송과 개인 정보를 분리 | 실제 게임 흐름에서도 비공개 범위 유지 확인 필요 |
| 그림 메모리 상태와 backend 영속 저장 분리 | 실시간 stroke 전파와 기존 DB·갤러리 재사용 | 주기 저장 전 강제 종료 시 최근 변경 유실 가능 |

| 10초 PING·5초 재접속·구독 복원 | 연결 이상 감지 및 재연결 지원 | 오프라인 메시지 이력 재생과 서버 재시작 시 게임 복구는 미지원 |

## 실제 검증 근거

- Redis 전환 최종 검증(2026-11-03): backend 관련 5개, socket 전체 22개 테스트 통과. 철회·실제 쓰기 순서, 비동기 그림 로드 후 차단을 보완하고 독립 정적 재리뷰 승인. 실제 Redis 전달 결과는 2026-11-04 항목을 참조.

- `tools/netty-smoke-result.json`: 실제 backend/Netty와 메모리 DB 기반 통합검사 11항목 통과 기록. 채팅·이동·그림/갤러리·주기 저장·방 격리·접근 거부·3인 마피아·퇴장 정리 포함.
- `.herdr/NETTY-REVIEW.md`: 이전 구현의 독립 정적 리뷰 기록. 운영 안정성 보증으로 해석하지 않는다.
- `tools/realtime-benchmark/REPORT.md` 및 `results/`: 동일 PC에서 1,000연결·100개 방×10명, 4개 생성기, 5초 워밍업·20초 측정·10초 drain. 채팅/이동/그림 각각 입력 1,000·5,000 msg/s에서 두 방식 모두 drain 후 누락·중복 0. 단기 로컬 관찰이며 지속 운영 보장이 아니다.
- 입력 5,000 msg/s의 방당 10명 fanout은 약 50,000 수신 delivery/s이며 입력 처리량과 구분한다. 세 workload를 동시에 합산한 혼합 부하가 아니다.
- Netty의 일반적인 성능 우위는 확인하지 못했다. 10,000 msg/s 목표는 생성기 지연·호스트 경합, Netty 스레드 관련 OOM과 후속 준비 실패가 있어 서버의 최대 처리량으로 쓰지 않는다.
- 총 최대 힙은 두 모드 1,536 MiB로 맞췄지만 Netty의 추가 인증·저장 경로 등 기능 비용은 동일하지 않다. 순수 I/O 엔진 비교로 쓰지 않는다.
- 브라우저 UI QA는 도구 정책 차단으로 미완료. 기존 소켓 통합검사를 UI 검증으로 표현하지 않는다.
- 권한 철회 구현 회귀검사: backend ACCEPT 철회만 이벤트 요청, AFTER_COMMIT/rollback, 공통 JSON fixture; socket 수신 전용 세션 종료·다른 사용자/방 보존·중복/잘못된 이벤트·인증 in-flight 경합·401/403 대 503 close code와 Redis-disabled context를 검증했다.
- 2026-11-04: Docker Desktop을 숨김 실행해 격리 Redis 컨테이너를 올리고, H2 메모리 backend와 Netty를 독립 JVM으로 붙인 `tools/redis-revocation-integration.py` 1회 통과. 기존 탈퇴 API의 ACCEPT→REFUSE commit, Redis 발행/수신, 대상 사용자만 종료, 같은 방의 다른 사용자 지속 채팅을 확인했다. 이 재실행은 실제 WebSocket CLOSE 제어 프레임의 코드 4403 및 reason `room access revoked`가 5초 내 도착하는 것과, 같은 유효 쿠키의 신규 연결이 backend에서 즉시 거부되는 것을 확인했다. timeout·일반 소켓 예외는 통과로 취급하지 않는다. 로컬 dev seed와 단일 서버 인스턴스 조건이다.

## 확인된 개선 대상 — 완료 성과로 쓰지 말 것

1. 주기 그림 저장을 실시간 방 큐에서 분리하면서 버전·스냅샷으로 변경 유실 방지.
2. RoomQueue slots와 SketchService walls의 안전한 미사용 상태 정리.
3. UNSUBSCRIBE와 방 퇴장 의미 정리, 연결 유지 시 presence 잔류 처리.
4. 인증 재검증 비용·동시 요청·스레드 사용 제한과 관찰성 개선. 이전 10k 부하에서 `HttpClient-1-Worker-*` uncaught `OutOfMemoryError`를 관찰했으며, 이 구현은 재검증을 분산하지만 부하 재검증을 하지 않아 OOM 해소를 주장할 수 없다.
5. 미인증 연결 수명·개수 제한. 현재 CONNECTED는 방 접근 인증 성공을 뜻하지 않음.

## 이력서 문장 초안

> Spring STOMP 기반 실시간 기능을 별도 Netty WebSocket 서버로 분리하고, 방별 비동기 명령 직렬화와 backend 권한 검증을 적용해 채팅·캐릭터 이동·공동 그림판·그림 마피아를 이식.

> 사용자 인증 수명과 그림 저장 수명을 분리하는 서버 전용 저장 자격 및 저장 성공 후 캔버스 초기화 정책을 설계하고, 방 격리·접근 제어·개인 역할 전달을 포함한 통합 시나리오 11항목 검증.

성능 수치는 필요할 때만 로컬 단기 시험 조건과 함께 덧붙인다. “Netty 도입으로 처리량 향상”, “운영 1,000명 보장”, “무손실·무중단”, “이벤트 루프 지연 개선”은 현재 근거로 주장하지 않는다.

| 강퇴 이벤트가 다른 사용자나 다른 방의 세션까지 종료할 수 있음 | 신뢰된 세션 사용자와 이벤트의 방을 함께 확인. 미확정 인증에도 해당 방의 인증 시도만 반영 | 최종 socket clean test·bootJar 통과, 27개 테스트 실패 0, 독립 리뷰 승인. 실제 Redis 통합은 최종 방 범위 수정 전에 통과했고 이후 재실행하지 않음 |

이력서 문장 초안:

> 분리된 Backend와 Netty 서버 간 방 권한 변경을 Redis Pub/Sub으로 전파하고, 인증 응답과 철회 이벤트의 경합을 제어해 늦은 인증 응답에 의한 권한 복구를 방지.

그림 저장 개선이 완료되고 실제 수치가 확보되면 사용할 문장:

> Backend 저장 지연이 방의 실시간 메시지 처리에 전파되는 구조를 개선하고, 버전 기반 스냅샷으로 비동기 저장 중 그림 변경의 정합성을 보장. 저장 응답 3초 지연 조건에서 채팅 p99 A → B 측정.

A·B는 실제 측정 전 자리표시자다. 요청 감소율, 지연 개선율, 운영 안정성 등 측정하지 않은 성과는 기재하지 않는다.
