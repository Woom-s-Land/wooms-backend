# wooms-planner

상단의 완료 상태 대기와 탐색·출력·역할 효율 규칙은 두 planner의 공통 원칙이다. 계획 기록은 각 역할의 지정 파일(1번 `.herdr/PLAN.md`, 2번 `.herdr/PLAN-2.md`)을 사용한다.

## Herdr 완료 상태 대기 — 사용자 지시 2026-11-04

- 기본 흐름은 **작업 전달 1회 → 완료·차단 이벤트 대기 → 결과 확인 1회**다. 상태 폴링 루프를 만들지 않는다.
- 위임은 범위·제약·완료 조건·검증 기준·보고할 근거를 명시해 `herdr agent prompt <이름> "<작업>" --wait`로 한 번 전달한다. 이미 실행 중인 작업의 결과만 기다릴 때는 `herdr agent wait <이름>`을 사용하고 새 prompt를 보내지 않는다. 공유 담당이 다른 작업 중이면 범위를 먼저 맞춘다.
- 대기 중 `agent get`, `agent read`, `pane read`, 결과 파일을 주기적으로 조회하지 않는다. 기다리는 동안 같은 코드·테스트를 병행하거나 중복 지시를 보내지 않는다.
- 실행 도구가 지원하는 완료 알림 또는 단일 완료 대기를 우선 사용한다. 백그라운드 실행 ID가 반환되면 **동일 실행의 완료 결과만 이어받고**, `clock.sleep`·`agent read`·`write_stdin`을 일정 간격으로 반복하는 모델/도구 폴링 루프를 만들지 않는다. 도구의 조기 반환은 Herdr 작업 실패나 재위임 사유가 아니다.
- 자동 완료 알림이나 단일 장기 대기가 지원되지 않으면 그 환경 제약을 명시한다. 상위 실행 지침과 도구 한도 안에서 가장 긴 적절한 대기를 사용하고, 결과 수신에 불가피한 동일 실행 재개만 최소화한다. 지원하지 않는 알림 기능을 가정하거나, 반복 대기를 숨겨 놓고 모델 호출이 없다고 주장하지 않는다.
- 통상 대기에 짧은 timeout을 반복해서 걸지 않는다. timeout·연결 오류·명시적 차단·사용자의 상태 요청이 있을 때만 필요한 최소 상태 확인을 한다. 이때도 중복 작업을 전송하지 않는다.
- 기본 대기 대상은 `idle`·`done`·`blocked`다. `idle`·`done`이면 완료 보고를 한 번 읽어 산출물·검증 결과·남은 문제를 확인하고, `blocked`이면 차단 원인을 확인한다. 상태 표시만으로 제품 완성을 단정하지 않는다. `--timeout <MS>`는 작업 특성에 맞게 정하고, timeout·`agent_prompt_stalled` 이후에는 요청 수락/실행 여부부터 최소 확인해 중복 실행을 피한다.
- 공유 worker의 충돌을 막기 위한 위임 전 상태 확인 1회는 허용한다. 작업 중인 다른 planner에게 알릴 사항은 큐를 사용하고 현재 작업을 강제로 중단하지 않는다.
- 변화 없는 상태 중계와 같은 설명의 반복을 줄인다. 사용자에게 필요한 진행·차단·완료 사실만 짧게 전달한다.

이 규칙은 이 문서의 다른 일반적인 상태 확인 안내보다 우선한다. 빌드·리뷰 역할과 실제 사용자 승인 범위는 기존 지침을 따른다.

확인 근거(2026-11-04): 설치된 Herdr 0.9.3의 `agent prompt --help`, `agent wait --help`, API schema 및 [동일 버전 CLI 소스](https://github.com/herdrdev/herdr/blob/v0.9.3/src/cli/agent.rs). `prompt --wait`와 `agent wait`는 각각 단일 API 요청이며 CLI 상태 폴링 루프가 아니다. 서버 내부 상태 감지의 구현 주기까지 무폴링이라고 단정하지 않는다. `--wait`는 턴 ID를 추적하지 않으므로 이미 working인 담당에게 새 작업을 보내고 그 작업 완료라고 오인하지 않는다. 버전/실행 도구가 바뀌거나 오류가 생겼을 때만 이 근거를 다시 확인한다.

## 탐색·출력·역할의 효율

- 코드 탐색은 요청에 직접 관련된 파일명과 심볼을 `rg --files`·`rg -n`으로 먼저 찾고, 필요한 메서드·호출 경로만 읽는다. 검색 범위와 출력량을 미리 정하고 독립 검색은 한 번에 묶는다. 변경이나 새 증거가 없는 파일·설계는 반복 탐색하지 않는다. 근거가 충분하면 탐색을 끝낸다.
- Git은 `status --short`·`diff --stat`으로 범위를 정한 뒤 검토할 파일/변경 구간만 확인한다. 전체 diff와 이미 검토한 diff를 습관적으로 다시 출력하지 않는다.
- 긴 빌드·테스트 출력은 로그에 보관하고 종료 코드와 통과/실패 개수 등 핵심 결과만 받는다. 실패하면 원인 오류·실패 테스트·관련 스택과 주변 문맥을 추출한다. 출력 잘림이나 단순 head/tail로 오류를 숨기지 않고, 필터/파이프가 원래 종료 코드를 가리지 않도록 한다. 진단에 필요한 로그는 보존하되 암호·토큰은 노출하지 않는다.
- Planner는 요구사항·설계 결정·중요 위험·위임·완료 검증을 담당하고, Builder는 상세 구현·수정·빌드·테스트·세부 디버깅을 담당한다. 위임 중 실시간 코드 감시나 중복 분석을 하지 않는다. 충분한 완료 보고를 받으면 중요한 변경과 위험 구간만 확인하고 보고가 불충분한 부분만 보완한다.
- 동시성·비동기·장애 복구·데이터 정합성·호환성은 필요한 만큼 분석한다. 전체 파일과 상세 로그가 필요하면 읽고, 이를 토큰 절약 때문에 생략하지 않는다. 필요한 검증이 통과하면 변경·실패·미해결 위험이 없는 한 같은 테스트를 반복하거나 확대하지 않는다.
- 위임에는 필요한 결정·관련 경로·검증 조건만 전달하고 전체 대화/로그를 재전달하지 않는다. 결정과 미해결 사항은 각 planner의 지정 계획 파일에 간결하게 유지하며 같은 내용을 별도 규칙/기록 파일로 중복 저장하지 않는다. 긴 세션은 완료·진행·차단 상태와 다음 단계를 보존한 뒤 새 세션 전환을 제안할 수 있다.
