# 현재 STOMP 처리율 기준선 측정

## 최신 사용자 요청
- 1,000 연결 / 방당 10명 / 100개 방을 실제 측정한다. 전체 입력 목표 1,000 msg/s(연결당 평균 1 msg/s), 워밍업 5초 / 측정 15초 / drain 10초로 우선 실행한다.
- Node22 생성기의 리뷰 오류를 먼저 수정하고 2연결 smoke를 통과시킨다. 같은 조건을 2회 실행하여 재현성을 확인한다.
- Node 생성기는 내장 WebSocket을 정상 호출하고 모든 구독의 고유 probe를 확인한 다음 측정 경계를 결정한다. 송신 루프는 반드시 주기적으로 yield한다. 관측하지 않은 event-loop/buffer 통계를 0으로 작성하지 않는다.
- 인증/브라우저 렌더링 없는 로컬 chat 테스트이며, 최대 처리량이나 실사용자 1,000명 전체 동작 보장으로 확대 해석하지 않는다.

## 목표
- Netty 전환 판단과 이후 동일 조건 비교를 위한 현재 Spring STOMP의 실제 로컬 처리율, end-to-end 지연 및 미수신 기준선을 측정한다.
- 제품 구현/설정/프론트는 변경하지 않는다. 자동 commit/push하지 않는다.

## 현재 동작
- Spring Boot 3.3.2, Java 22, `/ws` WebSocket 및 STOMP simple broker.
- `/ws/send/chat/{UUID}` -> `/ws/wooms/chat/{UUID}`: JSON ChatMessage 파싱 및 재직렬화, 메시지마다 INFO 로그.
- 이동/그림판/마피아도 STOMP 공유. 우선 chat 경로는 DB 변경 없이 실제 controller/broker/broadcast를 측정할 수 있다.
- 현재 8080 리스너는 발견되지 않았고 java는 PATH에 없음. 설치된 JDK/기존 빌드 도구를 탐색해 사용한다.

## 설계
- 실제 별도 JVM 서버와 별도 부하 생성기 프로세스로 측정. main 제품 코드는 그대로, 명령행 override로 H2 메모리 DB/독립 포트 등 로컬 기존 DB를 보호한다. 시작/종료한 자기 프로세스만 정리한다.
- 기본은 현재 dev 로그 수준 그대로 측정하고 결과에 명시. 로그 축소 비교는 선택적 별도 시나리오로 구분하며 기본 결과와 섞지 않는다.
- 각 메시지에 runId/publisherId/sequence를 넣어 고유 식별하고 monotonic clock 송신~구독 수신 지연을 기록한다. 동일 호스트에서 생성기 clock 사용.
- 먼저 SUBSCRIBE 준비를 probe 왕복 수신으로 확인한다. 워밍업과 본 측정 집계 구간을 분리한다.
- 실제 송신된 고유 메시지 수(ingress), 예상 fanout 수, 집계 구간 수신 delivery 수, drain 뒤 고유 수신/누락/중복/에러를 구분. 측정 시간과 drain 시간을 표기. 누락은 무조건 서버 유실로 단정하지 않는다.
- 작은 방 다수(예: 방당 5명, 총 10/50/100연결)와 한 방 fanout(예: 10/50/100연결)에서 단계별 송신률을 올린다. 최소 유의미한 3단계, 각 워밍업 5초+측정 15초 이상. 과도한 자원 사용은 중단/상한 적용.
- 입력 msg/s와 출력 delivery/s를 분리하고 p50/p95/p99(ms), 송신률 달성 여부, 미수신/중복/오류, 실제 연결 수를 보고한다. 가능하면 CPU/메모리와 생성기 event-loop lag/버퍼량을 수집해 생성기 병목 여부를 판단한다.
- 성능 최대치라고 단정하지 말고 측정한 범위 및 안정 조건(예: 누락 0, p99 <= 100ms)을 별도 정의해 결과를 해석한다. 가능하면 상한 가까운 조건 재실행.
- 인증 없는 연결을 쓸 경우 현재 endpoint 동작에 따른 제한적 익명 chat 경로 측정임을 명시하고 로그인 포함 측정으로 표현하지 않는다.

## 변경 파일과 제약
- `tools/stomp-benchmark/` 아래 재현 스크립트/최소한의 전용 의존성/README 및 요약 보고서를 작성할 수 있다. 거대한 raw 로그/DB/비밀은 저장소에 추가하지 않는다. raw 결과는 필요시 TEMP에 저장하고 요약 JSON/Markdown만 산출한다.
- `.herdr/PLAN.md`는 planner 소유. `.herdr/PLAN-2.md` 및 다른 담당 변경을 건드리지 않는다.
- 빌드/실행 장애는 근거와 시도한 해결을 보고한다. 무관한 제품 수정으로 해결하지 않는다.

## 검증
- 작은 smoke에서 기대 delivery와 실제 고유 delivery가 정확히 일치하는지 확인.
- 측정 스크립트 결과 집계와 지연/누락 산식 자체 확인.
- 환경(OS/CPU/메모리/JDK/서버 및 생성기 동일 머신/로그 설정), 실행 명령, 시나리오, 실제 수치, 한계를 보고서에 남긴다.
- builder 완료 후 reviewer가 스크립트와 측정 근거를 독립 검토한다.
